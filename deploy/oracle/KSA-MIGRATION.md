## Placement and cost

Use PostgreSQL 18 on the existing ARM VM with a Docker named volume. The app already uses Prisma's PostgreSQL provider, PostgreSQL types and 48 SQL migrations. PostgreSQL gets a 3 GiB ceiling, 512 MiB shared buffers, 4 MiB per work operation and 60 connections. Leave the other roughly 9 GiB for the kernel, Nest, Next, tunnel, cache and builds. Measure peak build, restore, query and backup loads and disk space for WAL, data, temporary files and images. This is one failure domain. Oracle can reclaim idle A1 instances after seven days when CPU p95, network and memory utilization all fall below 20%. Monitor those metrics and rehearse provisioning another VM from the independent vault. Replacement ARM capacity can be delayed. [Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

Autonomous Database moves patching off the VM. Always Free offers up to two 20 GB Oracle databases in a supported home region. Oracle's free-tier overview lists 20 sessions and its Autonomous service guide lists 30. Confirm the console limit and Jeddah availability if reconsidering. The Oracle SQL engine cannot run this Prisma PostgreSQL client, migrations or pg_restore archive. Adopting it would require an application port. [Autonomous service limits](https://docs.oracle.com/en-us/iaas/autonomous-database-serverless/doc/autonomous-always-free.html)

Use regional OCI Object Storage. MinIO would preserve S3 APIs but share the VM's disk, patch cycle and loss/reclaim risk. Reserve room for live assets plus 14 complete encrypted copies of both assets and database, uploads in progress and lifecycle delays. Always Free-only has 20 GB combined and 50,000 requests/month. Trial and paid tier splits differ. Check actual Standard entitlement and forecast requests including public reads before assigning a zero-cost budget. [OCI allowances](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

## Freeze and copy

Budget **120 minutes provisionally** for a small installation: 25 minutes for frozen dump/restore and indexes, 15 for asset copy/readback and URL updates, 20 for a full encrypted database and asset backup, 25 for an independent download/decrypt/restore, 15 for release and application verification, and 20 reserved for rollback. Time each phase with representative volume, object count and throughput before booking. If elapsed time reaches the rollback reserve before acceptance, keep writers fenced and roll back.

1. Enable maintenance mode on both public origins. Stop all API instances, queued workers, upload clients and scheduled tasks. Pause the old backup timer and wait for any running job. Confirm database and storage writes have stopped. Keep the old source frozen throughout verification. Use owner-controlled local scratch in Jeddah, mode 0700 and umask 077.
2. Run the copy commands from a disposable maintenance container joined to the candidate database network, with private profiles and Jeddah scratch mounted inside. For example, set GDG_RELEASE_DIR to the prepared release directory and use ./snapshot-run.sh --entrypoint sh -v "$SCRATCH:/work" -w /work -e PGSERVICEFILE=/work/pg_service.conf backup. Place libpq passfiles in the protected scratch directory and reference their container paths in the profiles. Use PostgreSQL 18 client tools. Use separate protected libpq service profiles called source and target. Source uses verified TLS and a direct or session connection. Target uses gdg_migrate. Confirm the database identity and empty target before restore. These commands omit the public schema creation entry because the bootstrap already creates and owns it.

```sh
set -eu
umask 077
PGSERVICE=source pg_dump -Fc --schema=public --file=public.dump
pg_restore --list public.dump > archive.list
sed '/ SCHEMA - public /d' archive.list > restore.list
PGSERVICE=target pg_restore --dbname='service=target' --use-list=restore.list --exit-on-error --single-transaction --no-owner --no-acl public.dump
PGSERVICE=target psql -X -v ON_ERROR_STOP=1 -c 'REVOKE ALL ON public._prisma_migrations FROM gdg_app'
```

## Independent recovery

Provision an empty Jeddah recovery bucket and fresh PostgreSQL volume in a separate Compose project. Give the restore principal read-only vault access and write/read access only to the recovery asset bucket. Use a dedicated HTTPS recovery origin that serves only that bucket. For personal data, restrict recovery reads to the drill network. Block the original public origin at the recovery network egress layer, including IPv6. Confirm a request to the original origin fails and the independent regional vault endpoint remains reachable. Run the recovery backend alone on an isolated Docker network or recovery host. Omit the production tunnel and use isolated mail capture, recovery origins and SCHEDULERS_ENABLED=false. The fixed production container name requires a separate host or a distinct name for the recovery backend.

Use a separate mode-0700 GDG_CONFIG directory with fresh postgres.env and restore.env from the recovery templates. Set ASSET_BUCKET and ASSET_PUBLIC_BASE to the recovery bucket and HTTPS origin, PGUSER to gdg_migrate with the recovery password, and VAULT_* to the original read-only vault. Use a dedicated project name and the same prebuilt release. Supply any remaining Compose env files from isolated fixture/config inputs. Keep the decryption identity mounted read-only for the drill.

```sh
export GDG_PROJECT=gdg-recovery
export GDG_CONFIG GDG_RELEASE_DIR RECOVERY_IDENTITY
docker compose --env-file "$GDG_RELEASE_DIR/tags.env" -p "$GDG_PROJECT" -f "$GDG_RELEASE_DIR/compose.yml" up -d --pull never --no-build --wait postgres
./restore-jeddah.sh "$SNAPSHOT_ID"
```

Restore authenticates the archived bytes, restores the public schema, uploads objects to the distinct bucket, and rewrites restored application rows using keys from the encrypted manifest. It reads an actual restored row, fetches its HTTPS image without redirects and compares its SHA-256 with the decrypted archive. A snapshot must contain a referenced image for this gate. On failure use a fresh recovery volume and empty bucket for the next drill. Retire recovery resources and temporary identity after verification.

## Rollback

Before any target-side business writes or scheduler side effects, stop the candidate, reinstate the previous private configs (including Supabase URLs, keys and frontend CSP), previous release and original backup unit/script/config together. Verify the old backend is sole writer and sign-in, QR and public image reads succeed before reopening. If candidate activation failed before the current-release pointer moved, use the recorded former release directory directly. Check effective config before starting the old backend. Keep the maintenance fence active during failure handling.

After target writes, freeze again and preserve both stores. Reconcile new or changed records, sequences, sessions, uploads, URL mappings and externally delivered jobs before switching back. For URL reversal, in the protected maintenance client with PGSERVICE=target run `python3 /opt/gdg/backfill-assets.py --reverse`. It matches table, primary key and current migrated value and marks reverted mappings transactionally. Inspect unreversed records for subsequent edits or deletions. This command changes URLs only; reconcile file content and other records separately. Obtain owner approval for any reverse transfer outside KSA. After acceptance and the agreed rollback period, remove foreign copies, credentials and local scratch under the owner's retention policy.

## Maintenance

For password rotation, pause the affected client, connect interactively as the database administrator through Compose exec postgres psql -U postgres -d gdg and use psql's password prompt (for example, `\password gdg_backup`). Update the corresponding private backup, application or migration connection and bootstrap password record together. Recreate affected clients, test a new connection and resume. Changing postgres.env alone cannot rotate an initialized role. Rotate the bootstrap administrator through its live role in the same way.

For a PostgreSQL major upgrade, prepare a separate digest-pinned server and matching client image with a fresh volume. Retain the previous image set and volume. Verify extension compatibility, rehearse logical dump/restore, default privileges and an independent encrypted recovery. During an approved freeze repeat the copy and verification gates before repointing the application. Use the same pre-write versus post-write rollback boundary. Never attach the previous data directory to a new major server.
